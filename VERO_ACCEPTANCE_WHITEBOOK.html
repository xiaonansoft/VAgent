摘要（结论先行）

工业界正在进入"数字员工"叙事的高峰期。大量公开材料展示了协同演示与组织图景，但几乎找不到一条可以被第三方复算的量化指标——这既是行业当前的普遍状态，也是最大的风险：如果验收范式被默认定义为"看协同演示效果"，整个行业会被拖进演示军备竞赛，首期靠声量签单的项目，会在二期死在"它到底干成了什么"这一问上。

本白皮书提出一套可落地的三层验收模型（确定性底座 / 决策质量 / 业务结果）、一份每个数字都标明出处与口径的可承诺指标表、一条逐条可审计的工程红线，以及一套争议仲裁规则。VERO 愿意并且愿意以自己的真实数据接受这套标准的检验——有真实数据的地方给数字，没有的地方写"（待采集）"，不把形容词当指标。

01 · 为什么需要一套验收标准

1.1 三个正在发生的现状

现状描述后果
无 KPI 的叙事 公开材料里大量存在"提升效率""降低劳动强度""实现协同"这类表述，但找不到分母、判据、统计区间和数据来源。 甲方无法比价，只能比 PPT；乙方被迫加大演示投入而非产品投入。
演示态冒充生产态 在精心挑选的炉次、人工补齐的数据上跑通的流程，通常在验收文档里与真实产线表现混为一谈。 上线三个月后信任崩塌，比不上线更伤。
演示军备竞赛 当"有多少个角色、能联动多少环节"成为比拼尺度，架构上越激进的方案越容易在演示中显得先进。 劣币驱逐良币：稳健的单引擎架构在叙事上吃亏，多智能体交接的风险被隐藏。

1.2 两类必须被拦住的表述

类型一：「联动更新全部控制参数」
这句话有两种读法。合规读法＝约束变化时全链路重算、输出新建议包、交人确认；危险读法＝系统直接改写控制回路设定值。危险读法一旦落地，意味着一条未经确认的数据获得了改变工艺设定的权限；跨设备分布式写入没有事务，写一半失败时炉子处于未定义参数组合。验收条款必须把这两种读法分开写、分开罚。

类型二：「由 XX 数字员工完成计算 / 交接 / 决策」
角色一旦进入执行链路，责任主体就模糊了。事故复盘时会出现标准句式——"是数字员工建议的"。验收必须要求：留痕中不存在人称主语，只有系统标识、模型版本、工具名称与时间戳。

1.3 本白皮书的三条主张

主张一
验收分三层，不可跳层
先看确定性底座是否成立（能不能复现），再看决策质量（人能不能安全地推翻它），最后才看业务结果。没有 L1 的 L3 是运气。
主张二
没有真实数据的指标不许填
指标表允许出现"（待采集）"，不允许出现"预计""有望""较大提升"。承认无知，是工程可信的最低门槛。
主张三
红线要写成可查询的计数
不用"原则上不允许"这种措辞，用"LLM 直接下发设定值次数＝0，可随时审计"。

02 · 三层验收模型

三层之间存在单向支撑关系：L1 不成立时，L2、L3 的漂亮数字都不可信；L2 不成立时，L3 的短期改善不可持续（因为没有纠错通道）。

L1 · 确定性底座（Deterministic Foundation）

回答的问题：同样的输入，是不是永远给出同样的输出？每一次变更，能不能被复算出来偏差在哪？

验收项判据验证方式
黄金回归每次知识包 / 模型版本变更，回归用例必须全通过；当前基线 75/75，最大误差 0.0002%在甲方见证下现场执行回归脚本，输出 pass/fail 与误差分布
可复现同一输入 + 同一版本号 ⇒ 同一输出，两次调用结果逐字段一致同一炉次数据重放两次，逐字段比对（含中间量）
版本可追溯任意历史建议包可反查出：model_version / pack_version / trace_id / 输入快照随机抽 5 个历史炉次，30 分钟内给出完整溯源链
双端一致性同一模型的两种实现（如 Python 服务端 / 前端 JS）结果一致；当前基线 JS 端 11/11 与 Python 完全一致parity 校验脚本，漂移时输出红灯而非静默
数值溯源输出中的每一个数字必须来自工具调用返回值；溯源失败则拦截拒答随机抽取输出项，逐一点击查看公式 + 数据来源 + 时间戳

L2 · 决策质量（Decision Quality）

回答的问题：当人不认同系统时，能不能安全、低成本地推翻它？系统会不会从被推翻中变好？

验收项判据验证方式
建议不强制所有影响工艺参数的建议在交付前必须经人工确认；不得存在绕过确认门的执行路径静态检查 + 渗透测试：尝试构造直达执行的调用路径，应当失败
推翻留痕每个建议提供【推翻】入口；推翻事件记录：建议值 / 实际值 / 理由分类 / 时间戳 / 操作人（岗位）抽查留痕记录，字段完整率 100%
推翻仲裁自动化推翻对错由机理引擎回溯铁数据判定（终点温度 / 终点碳 / 喷溅记录 / 化验实绩），不由专家拍板抽取已结案推翻事件，核对判定依据字段是否来自数据源而非人工填写
推翻后命中率运营观测指标（定义见 §04），不设为罚款条款月度运营报表
建议留痕完整率每一条对外建议都入留痕管道，无旁路比对引擎调用计数与留痕条数，差值为 0

关键设计：不考核采纳率。理由见 §04。

L3 · 业务结果（Business Outcome）

回答的问题：炉子到底更好了没有？钱到底省在哪里？

验收项判据数据门槛
终点命中率终点判断结果与工艺判定一致的炉次占比（判据须在合同中写死：温度窗 / 碳窗 / 是否需补吹）统计样本量下限（待基线采集后确定，建议 ≥100 炉）；新炉座、原料结构重大变化时重新起算
钒回收率进入钒渣的钒量与铁水带入钒量之比基线值（待采集），需先统一化验口径与取样规则
例外炉次率触发例外流程（黄灯及以上）的炉次占比基线（待采集）；趋势下行即视为改善，不与惩罚挂钩
单炉经济效益按"配吃结构优化 + 回收率提升 + 返工/补吹减少"三项加总，逐项列出计算表测算口径随数字一同交付；任何单项不得单独抽出来宣称

04 · 双轨 KPI 与四周基线期规则

4.1 为什么坚决删除采纳率

采纳率作为 KPI 会导致两个确定性后果：

  1. 系统侧：为保采纳率，系统会自我保守化——只挑没有争议的建议推送，最需要提醒的例外工况反而沉默。
  2. 人的侧：KPI 落到班组，终点就是逼操作工点确认。操作工被训练成橡皮图章的那一刻，AI 的错误就被洗白成了人的决策——责任链断裂，且不可逆。

因此：采纳率从 KPI 体系中永久删除，不作为付款条件、不作为班组考核项、不作为验收指标。

4.3 推翻判定的三条铁规则

规则一
机器回溯，不由专家拍板
推翻对错由机理引擎自动回溯铁数据判定：终点温度 / 终点碳 / 喷溅记录 / 化验实绩。不让任何人在当时当地的情绪下做裁判。
规则二
推翻正确＝给引擎上课
判定"推翻正确"的样本自动进评测集，作为下一次模型/知识包变更的必过用例；判定"推翻错误"的进培训案例。被推翻不是污点，是燃料。
规则三
奖励发"面子"不发钱
适配国企：月度会公开念名 + 免责记录（该次推翻已被判定正确，不因偏离建议追责）。不承诺现金。

4.4 4 周基线期规则

周次做什么禁止做什么

05 · 红线条款（可直接进合同附件）

第 1 条 · 不下发设定值。乙方系统不得以任何形式向 L1/PLC/DCS 控制回路下发设定值或执行指令。可审计判据：「LLM 直接下发设定值次数 = 0」，甲方可随时通过日志查询验证；IControlSignalWriter 永不提供真实 DCS 实现。
第 2 条 · 数值必须溯源。乙方系统输出的全部数值必须来自确定性工具调用返回值。溯源失败时系统必须拦截并拒答，不得以任何方式给出"估算值""参考值"。LLM 不承担数值计算职责。
第 3 条 · 零人格化留痕。所有留痕、操作记录、审计日志中不得出现人格化主语（人名、昵称、"数字员工/AI 同事/虚拟班组"等）。主语只允许："系统 / 机理引擎 / 模型 vX.X / 数据来源·接口·时间戳"。
第 4 条 · 确认门不可绕过。所有影响工艺参数的建议节点后必须挂人工确认门；乙方以 CI 静态检查拒绝任何绕过路径合入。甲方有权进行渗透测试，构造直达执行路径应当失败。
第 5 条 · 口径冲突必须登记。规程、文献、厂级标准之间存在冲突的参数，必须在口径登记册（CF-001 ~ CF-008 及后续）中登记：冲突双方、证据来源、仲裁结论、生效版本。未登记的冲突不得在系统中静默取值。
第 6 条 · 数据质量自曝义务。数据存在缺失、延迟、超范围时，系统必须显式标注（来源 / 时效 / 完整度），并沿下游计算链路传染标记；不得用默认值冒充实测值。

争议仲裁以数据回溯为最终裁定依据：以 trace_id 拉取输入快照、模型版本、知识包版本、工具调用链，重放并比对。重放结果与实际留痕不一致时，以留痕为准（保证：留痕不可篡改）。裁定不由任何一方专家单独拍板。

退出条款连续两个核算周期未达承诺值且非甲方数据原因，甲方有权要求退回本阶段款项或终止合同——敢写退出条款，是这套指标可信的最好证明。

07 · 附：给甲方的「数字员工招标参数建议」清单

以下 10 条可直接复制粘贴进招标文件的技术评分/符合性条款。VERO 全部满足；这十条中每一条都对应一个真实存在过、且被公开材料反复踩到的坑。

#建议条款（可直接复制）为什么必须有这条VERO 满足情况多数对手难点
1 投标方须提供确定性底座证明：核心工艺模型须通过回归测试，并提供加权用例数、允许误差、最近一次回归时间与输出件。 区分"机理模型"与"Prompt 包装"的唯一硬办法。 满足75/75，误差 0.0002%，可现场复跑 无回归体系或不敢公开

3 系统输出的每个数值须可溯源至工具调用返回值 + 公式 + 数据来源 + 时间戳；溯源失败须拒答而非估算。 防 LLM 数值幻觉（编一个终点温度就是一次事故）。 满足架构红线硬保证 依赖 LLM 自由输出的方案做不到

5 投标方须提供角色协作的架构说明：角色是独立智能体还是同一引擎的多视图？若为多智能体，须说明交接协议的结构化字段与失败重试机制。 多智能体自然语言交接＝有损压缩 + 幻觉注入点。 满足单引擎多视角，无交接链 以"多角色协同"为核心卖点者难以解释

08 · 术语与数据口径声明

术语本白皮书口径
数字员工本文采用保守定义：能够稳定承担某一岗位部分职责（读取、计算、校核、留痕）的软件能力集合。人格化表述仅在管理层沟通与市场材料中使用，不进入执行链路与留痕。
单引擎多视角架构VERO 采用的拓扑：角色是数据的视图，不是独立的智能体；所有视角读取同一份带 trace_id 的计算结果，不存在交接幻觉链。
行业通用指跨厂一致的规则层级（对应知识包 industry 层）。VERO 是面向提钒冶炼行业的行业级产品，不是单厂定制项目；厂级差异通过覆盖层（plant_b / plant_a）承载。
确定性与红线确定性＝同样输入同样输出的成因计算；LLM 只承担语言层任务（意图识别、证据组织、解释生成），不承担数值计算与执行。
（待采集）指 VERO 当前尚无经过可验证数据源采集的指标。本文禁止以估算值填充；相关字段在获得基线数据后于本表更新。
（示例值）指可用于谈判讨论、但尚未经双方确认的建议取值，不得直接写入合同。
